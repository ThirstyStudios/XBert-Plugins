# XBert Agents + Plugins Test Results — v3 (LLM-in-loop, local MCP)

Date: 2026-05-26

Methodology: Each agent's `Instructions` (from `SystemAgentBase`) or plugin's `commands/<cmd>.md` was read by an LLM-in-loop subagent that walked the methodology section by section, searched the **local MCP gateway** (`https://localhost:7200/mcp` via `audit/local-mcp.ps1`) for tools satisfying each section, and invoked one critical tool per agent against client tenant 11668 (Peak Precision Accounting, GB) to confirm real data flows. Mock-user session: connectTenantId=11374, userProfileId=1.

- `Data_FixedAssets_Search/Summary/Get` updated: optional date filters, register-vs-window distinction documented, new `status`/`searchTerm`/`assetType` filters, singular `id` alias on Get.
- System agent Instructions sweep (strip hard-coded tool names → generic data-needs language).

## Sub-tier highlights

### WORK tier (capability gaps)

- **/mtd-ready** (agent) — MTD-ITSA is structurally different from VAT/BAS/GST/IAS - it needs an HMRC SA103/SA105 category mapping that XBert does not yet expose as a first-class concept. Agent could produce a hand-wavy 'looks ready / looks not ready' answer purely from COA pattern matching, but core capability for an actual readiness assessment is missing.
  - Recommendation: ticket-gap-build-MTD-ITSA-readiness-endpoint-with-HMRC-category-mapping
- **/cross-sell-opportunities** (agent) — Core lookalike-peer requirement has no direct MCP tool - Data_FindSimilarClientTenants is name-only, not industry/size/transaction-profile similarity. Agent must construct its own peer model from XPMClients + tags + notification profile, which is fragile. Service-mix and notification data are available, but the matching primitive is missing.
  - Recommendation: needs-tool
- **xbert-bill-intake** (plugin) — Read paths (dedup search + contact lookup + task creation) work. Critical write paths (OCR, supplier create, AI coding, bill posting) have NO MCP tools — the plugin cannot complete its stated end-to-end loop today.
  - Recommendation: rework: either narrow scope to 'dedup advisory + task creation' (drop OCR/coding/posting from v1) or build the missing extraction + coding + Bills_Create + Contacts_Create endpoints. As-written the command makes promises (post the bill, predict codes) the local gateway cannot keep.
- **xbert-cross-sell-opportunities** (plugin) — Core methodology requires a per-client lookalike-by-profile engine. The only 'similar' tool on the gateway resolves names — not industry/size/service-pattern peers. Cannot produce ranked lookalike-driven opportunities without that. XPM service uptake is partly available. Advisory triggers + client list both fine.
  - Recommendation: needs-new-tool: add Data_FindLookalikeClientsByProfile (or equivalent) before this plugin can deliver its stated output
- **xbert-reconcile** (plugin) — The plugin asks for a matching engine that doesn't exist in MCP. Without a 'propose matches' tool, the LLM is reduced to surfacing unmatched lines and asking the user, which is a thin value-add over Xero itself. The actual matching needs ledger entries (contacts, GL accounts, prior reconciliations) cross-joined to bank lines — substantial backend work.
  - Recommendation: extend-tools (need Data_BankReconcile_ProposeMatches and Features_ApplyReconciliation; OR rescope plugin to 'unmatched-lines triage' only)

### review tier (partial fit)

- **/billing-review** (agent) — All four reporting surfaces the agent describes (job billing, timesheet billable %, write-off %, profitability) hinge on XPM data. The summary endpoint is feature-flagged off in the local stack and the test tenants have no XPM rows, so the agent can only partially execute end-to-end. Once the flag flips and a client connects XPM, the core path works.
- **/reconcile** (agent) — Status + unreconciled-list + data-quality flows are all covered, but the two value-add sections (duplicate scan, proposed matches) have NO native tools - the agent must do heavy client-side reasoning over raw bank-transaction rows. Output remains useful but the 'match-batch for one-click approval' promise overreaches the available data.
- **/withholding-review** (agent) — Core payroll + GL withholding data is covered, but BAS labels W1-W5 have no first-class tool. Agent can synthesise from PayRuns_Summary tax totals + BankTransactions_Summary salesTaxBasis, but this is reconstruction work the prompt does not name. Otherwise sound.
- **/practice-metrics** (agent) — Core financial sections (revenue, AR, AP, P&L, cohort, tags, notifications) all work. XPM timesheets summary is currently gated on the local stack, so billable utilisation is a graceful-degrade case the agent already promises to handle.
- **/client-onboard** (agent) — Core practice-setup and template tools work; engagement/configuration phase gates have no first-class tool so phase must be inferred. Otherwise fully serviceable.
- **/instalment-variation** (agent) — Data side (P&L, BS, cashflow, budget, tax rates) fully covered. ATO instalment-notice ingestion is missing by design - agent treats the notice as user input.
- **xbert-aged-receivables** (plugin) — Core scoring inputs all present (aged summary + invoice search + contacts + tasks/notes). The skill's prior-promise weighting and outbound customer-reminder delivery have no first-class tools and must be approximated.
- **xbert-balance-sheet-explain** (plugin) — All core data layers exist. The skill's named 'validation result' tools (BankRec validation, BS review validation) do not exist as first-class endpoints; must be composed from ReconciliationStatus + XBertNotificationSummary.
- **xbert-bas-prep** (plugin) — Core blocking-XBert and bank-rec data is there. GST label, PAYG W1-W5, and BAS variance are not first-class; the plugin currently relies on the agent to derive ATO-form labels from primary data.
- **xbert-client-onboard** (plugin) — Orchestration tools (tasks, templates, schedules, client list, connection state, org settings) all present and working. Gaps: no 'create client note' surfaced cleanly in search, and 'apply rule baseline pack to client' must be assembled from BulkUpdateXBertConfigurations rather than a single 'assign rule pack' call. Both gaps are workable.
- **xbert-end-of-period-dashboard** (plugin) — Most coordination data is present (clients, DQ score, lock dates, work board, notifications, bank recon). BAS/VAT reconciliation 'validation' is a methodology-level assembly — the dashboard must compute it from BankTransactions_Summary (salesTaxBasis field) + PayRuns_Summary + ReconciliationStatus rather than calling one validator. Workable but pluginis carrying the reasoning load.
- **xbert-gst-prep-nz** (plugin) — Block/release logic is well served (outstanding XBerts + bank rec + control accounts). The GST101A box compute relies on derivation from bank-transaction salesTaxBasis rather than a first-class NZ tool; acceptable but skill becomes more complex.
- **xbert-ias-prep** (plugin) — Payroll-driven IAS prep is mostly covered via pay-run summaries + balance sheet control accounts + outstanding XBerts. Label compute (W1-W5, T7/T11) is the skill's responsibility — no native ATO-label tool exists. Workable but more derivation than the equivalent BAS plugin.
- **xbert-instalment-variation** (plugin) — Data inputs are well-covered (P&L/BS/cashflow/budget/tax rates). The recommendation engine (vary up/down/stay, GIC exposure, confidence label) is intentionally skill-owned — fits the 'never submit on behalf, partner sign-off if Needs review' guardrail.
- **xbert-mtd-prep** (plugin) — GB-only: tested against 11668 (Peak Precision Accounting, GBP, VAT/PAYE/NIC/CIS — real GB ledger). Core data (COA + P&L) is available; HMRC-mapping logic is entirely skill-owned (correct — HMRC SA103/SA105 category lists belong in domain skill, not MCP). Workable but heavy on skill-side derivation.
- **xbert-practice-health-check** (plugin) — All required data exists, but the plugin's worst-case (whole portfolio) is N×2 round trips because there's no Connect-level DQ/notification aggregator. Methodology is sound; performance gap is real but mitigated by GetClientConnections being single-call.
- **xbert-practice-metrics** (plugin) — Most metrics covered, but two structural issues: (1) no dedicated 'internal time' (non-XPM staff time) tool — plugin must approximate with ReviewActivity, weakening the service-line P&L; (2) per-client loop required for portfolio-wide invoices and AR (no Connect-level invoices summary). Will work but commentary depth depends on XPM being connected.
- **xbert-pulse** (plugin) — All the math works from BankTransactions_Summary.byMonth, but with no Connect-level aggregator the 'whole book' default in the command (step 1) is expensive. Threshold logic (±30%) is fully client-side from existing data. Suggested outreach drafting (step 7) has no MCP support and stays as LLM-only output — acceptable for v1.

## Cross-cutting findings

1. **`Validation_*` tools registered in canonical-241 but NOT in local MCP gateway** — `Validation_BankReconciliation`, `Validation_PayrollReconciliation`, `Validation_SuperReconciliation`, `Validation_BalanceSheetReview`, `Validation_BASReconciliation`, `Validation_VATReconciliation`. Several agents fall back to manual reconciliation via raw FS reads as a result. (Surfaced by agents-batch-3 on `/payroll-reporting-review`.)
2. **No jurisdiction-specific compliance-label calculator family** — NZ GST101A boxes, ATO BAS W1-W5 / G1-G11 / 1A-1B labels, HMRC SA103/SA105 categories. Agents/plugins derive these from raw `BankTransactions_Summary.salesTaxBasis` + `PayRuns_Summary` instead. A `Validation_*` or `Compliance_*Labels` family would let the related plugins drop a lot of derivation logic. (Surfaced by plugins-batch-3 on `/gst-prep-nz`, `/ias-prep`, `/mtd-prep`.)
3. **XPM summary endpoint feature-flag gated locally** — `XBERT_MCP_DATA_XPM_TIMESHEETS_USE_SUMMARY_ENDPOINT=false` blocks billing-review / practice-metrics from running end-to-end on local. Flag flip + XPM-synced test tenant would unblock both.
4. **No "lookalike client" similarity model** — both `/cross-sell-opportunities` surfaces (agent + plugin) scored WORK because `Data_FindSimilarClientTenants` resolves by name only, not by industry/size/transaction-profile. A real similarity model would convert both surfaces from WORK to KEEP.
5. **Bill-intake pipeline incomplete** — `xbert-bill-intake` plugin promises end-to-end posting; OCR, `Contacts_Create`, AI account/tax coding, and `Bills_Create`/`Post` are all missing from local MCP. Either rescope to dedup/triage only, or wire the pipeline.
6. **Bank reconciliation matching engine** — `/reconcile` (agent + plugin) needs `Validation_BankReconciliation` (canonical but unregistered) plus a "propose match"/"apply match" pair. Today agent does heavy client-side reasoning over raw transaction lists.
7. **No Connect-level roll-up tools** — `/practice-health-check`, `/pulse`, `/practice-metrics` all need N×2 per-client loops (one per client × per data type) because there's no aggregator. Scales poorly past 20-30 clients per portal.
8. **`Data_LedgerForShare` removal: zero impact** — confirmed in 70/70 audits. No agent or plugin referenced it.

## Methodology caveats

- All invocations against client tenant 11668 (Peak Precision Accounting, GB). Mock-user only has 3 accessible clients (11668, 11377, 11673) — AU/NZ-specific tax-rule branching for some agents was not exercised end-to-end.
- "WORK" tier reflects MCP-tool gaps, not agent quality. Some WORK items (e.g. mtd-ready, bill-intake) describe agents that are well-written but blocked by a missing backend tool.
- "review" tier is the largest spread — covers everything from minor cosmetic gaps (one tool returns no data on seed) to genuinely partial coverage (one section missing entirely).
- All `/command` lookups used the DB Instructions (agents) or `commands/*.md` (plugins) as the source of truth — no shortcuts to keyword search alone.
